# Let VOID Speak Only When It Matters

VOID should wake itself with a **two-stage design: a per-notification importance score computed on the phone, and a pressure-plus-context gate on the Mac that decides when to speak**. A small set of "breakthrough" classes (incoming calls, alarms, OTP/2FA arrivals, security alerts, priority-conversation messages) can wake VOID from a single notification. Everything else adds to a decaying pressure total that must cross a threshold, and only when the Mac is in a speakable state. The evidence base is uneven. Android's listener API is documented well enough to build the score, but three assumptions carry the most risk and must be tested on the real phone first. Android 15+ redacts 2FA content from ordinary listeners. How WhatsApp, Gmail, UPI and delivery apps fill their fields is unsourced. Android's contact-frequency columns are dead, so "close friend" must come from starred contacts, the "priority conversation" flag, and VOID's own history. On timing, research supports short holds to a breakpoint (about 90 s in one study), a hard maximum wait, and rare digests rather than per-item speech. No published study gives decay half-lives, cooldowns or thresholds, so every number in the plan is a starting value to tune. Spoken output should follow Siri's and Alexa's pattern (earcon, one-breath headline, 2 to 3 items, one question), hide message bodies on speakers, and never let the 0.8B model paraphrase claims. Reminders should be stored as absolute-time records, re-checked on every wake and clock event, and re-evaluated against live notification state when they fire. This report labels each claim as **Sourced** (from the research notes, with a link) or **Design inference** (my reasoning, to be validated).

## Android hands a listener category, channel, conversation and DND signals, but hides the best ones

**Sourced.** Per-notification, the dependable app-declared fields are the category string, the channel, MessagingStyle extras with `Person` objects, `shortcutId` and the flags bitfield. Category constants relevant to VOID have raw values you must match through the constants, not by guessing: `CATEGORY_CALL="call"`, `CATEGORY_MESSAGE="msg"`, `CATEGORY_ALARM="alarm"`, `CATEGORY_ERROR="err"`, `CATEGORY_PROMO="promo"`, `CATEGORY_MISSED_CALL="missed_call"`, plus `CATEGORY_REMINDER`, `EVENT`, `SYSTEM`, `PROGRESS`, `SERVICE`, `STATUS` and `RECOMMENDATION` ([AOSP Notification.java](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/main/core/java/android/app/Notification.java)). The flags include `FLAG_INSISTENT` (repeats until cancelled, used by alarms and calls), `FLAG_GROUP_SUMMARY`, `FLAG_ONGOING_EVENT`, `FLAG_FOREGROUND_SERVICE`, `FLAG_ONLY_ALERT_ONCE`, and on Android 16 `FLAG_PROMOTED_ONGOING` (same source). Call notifications using CallStyle carry `EXTRA_CALL_TYPE` and `EXTRA_CALL_PERSON`, and messages carry `EXTRA_MESSAGES`, `EXTRA_IS_GROUP_CONVERSATION` and `EXTRA_CONVERSATION_TITLE` (same source). `Person` exposes `getKey()`, `getUri()`, `isBot()` and `isImportant()` ([AOSP Person.java](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/main/core/java/android/app/Person.java)). The source caveat is that the notes read the GitHub mirror of AOSP because developer.android.com was blocked, and that mirror may lag Google's internal branches. The API-level numbers in the notes came from model recall and are unverified.

**Sourced.** The `Ranking` object adds the system's view: effective `getImportance()`, `getChannel()`, `matchesInterruptionFilter()` (does the user's DND rule allow it), `isAmbient()`, `isSuspended()`, `isConversation()`, `getConversationShortcutInfo()`, `getLastAudiblyAlertedMillis()`, `getUserSentiment()`, smart actions and smart replies. Channel getters include `canBypassDnd()`, `isImportantConversation()`, `isDemoted()` and `hasUserSetImportance()` ([AOSP NotificationListenerService.java](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/main/core/java/android/service/notification/NotificationListenerService.java); [AOSP NotificationChannel.java](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/main/core/java/android/app/NotificationChannel.java)). Unavailable to a normal listener: the system ranking score, proposed importance, the sensitive-content flag, `isNoisy`, and the `Adjustment` API, which is `@SystemApi` and reserved for the notification assistant ([AOSP Adjustment.java](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/main/core/java/android/service/notification/Adjustment.java)). The contact-affinity columns `TIMES_CONTACTED` and `LAST_TIME_CONTACTED` "always contain 0" since Android Q, while `STARRED` still works ([AOSP ContactsContract.java](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/main/core/java/android/provider/ContactsContract.java)).

**Sourced.** Two platform changes matter most. First, Android 15 hides the content of 2FA-code notifications from untrusted listeners, who see "sensitive notification content hidden"; the permission `RECEIVE_SENSITIVE_NOTIFICATIONS` is held by system-signed apps and by apps in the watch, glasses and default-launcher roles. Known workarounds are turning off "Enhanced notifications" (which also removes smart actions and replies) or granting access through an ADB appops command ([Android Authority](https://androidauthority.com/android-15-two-factor-authentication-codes-3492585)). Second, Android 13 blocks enabling a notification listener for sideloaded apps until the user allows restricted settings in App info ([Android Authority](https://www.androidauthority.com/android-15-sensitive-notifications-3416414)). Since the companion app is a personal sideload, both apply to VOID directly.

**Design inference.** The strongest "close friend" signal available is `ranking.channel.isImportantConversation()`, because the user set it deliberately. Next come `Person.isImportant()`, a `Person.getUri()` that matches a starred contact, and a locally computed affinity from `CallLog` and SMS counts (these need `READ_CALL_LOG` and `READ_SMS`, which are fine for a sideload) plus VOID's own record of which senders the user opens or replies to. For OTPs on Android 15+, the redaction is itself the signal: if the body equals the placeholder while the sender or title remains, classify it as "a code arrived from X" and speak only that. Reading SMS through `READ_SMS` may bypass the redaction, but that is unverified. Calls are easy: `CATEGORY_CALL`, CallStyle extras, `FLAG_INSISTENT` or a full-screen intent. Group summaries should be dropped and updates deduped on `sbn.getKey()` plus a hash of the newest message.

**Gaps that block a confident build.** The notes found no source for how WhatsApp, Telegram, Gmail, GPay, PhonePe, Swiggy or Zomato fill category, `Person.uri`, `shortcutId` or channel ids. Their expected behaviour (MessagingStyle with conversation shortcuts for chat apps, separate channels for order status and marketing) is inference only. The exact placeholder string, whether Samsung or Xiaomi phones apply the same redaction, and whether it fires on Hinglish bank SMS are also unknown. Hence the logging step at the end of this report is the first deliverable, not an afterthought.

## India's SMS headers give a cheap, deterministic spam filter, and Android's own promo classifier will not help

**Sourced.** Since 6 May 2025, TRAI-mandated SMS headers follow `[operator+circle]-[HEADER]-[type]`, for example `VM-BANK-T` or `KA-ZOMATO-S`. The suffix is added automatically from the DLT template: **-P promotional, -S service, -T transactional (bank OTPs and alerts), -G government**. The old "service explicit" category was retired and defaults to -P ([Storyboard18](https://www.storyboard18.com/how-it-works/why-your-sms-now-looks-like-a-code-trais-new-message-format-explained-70270.htm); also [India TV](https://www.indiatvnews.com/technology/news/understanding-sms-suffixes-what-s-g-p-and-t-mean-and-how-they-help-you-avoid-scams-2025-08-29-1005732) and [Tanla](https://www.tanla.com/udayreddy/trai-mandates-new-message-suffixes-heres-what-you-need-to-know)). In contrast, Android 16 QPR2's Notification Organizer, which moves promos, news and social items into system channels (`android.app.promotions`, `android.app.social`, `android.app.news`, `android.app.recs`), shipped on Pixel 9 and later (not the 9a), English only, in Australia, Canada, Germany, Japan, the UK and the US ([Tech Advisor](https://www.techadvisor.com/article/3006632/google-pixel-phones-get-notification-organiser-in-android-16.html)). The notes could not confirm whether it reaches India or non-Pixel phones.

**Design inference.** Treat those channel ids as a free low-priority signal if they ever appear, but do not depend on them. For SMS, parse the sender header with a pattern like `^[A-Z]{2}-[A-Z0-9]{3,9}(-[PSTG])?$`: -P drops to near zero weight, -T becomes a candidate for the OTP and bank-alert checks, -S is medium (order and delivery updates), -G is medium-high, and a plain 10-digit or +91 number is a person (check contacts) or unknown. A fixed operator-prefix list is not needed because the regex only requires two capital letters; the notes did not retrieve the official prefix list. The 140 and 1600 number-series rules were also not covered. Promo keywords ("% off", "cashback", "coupon", "free delivery") should be additive low-confidence cues only. Where the system gives no promo label, learn per-(package, channelId) open and dismiss rates, which substitutes for the hidden `KEY_USER_SENTIMENT`.

## Scoring: breakthrough classes bypass accumulation, everything else adds pressure

**Design inference** (no source publishes weights; the research only informs the feature choice). The best-supported feature families come from importance-prediction work: sender relationship, app or notification type, content, and thread state. Gmail Priority Inbox used social features (the share of a sender's mail the user reads), content terms, thread involvement and labels, in a global logistic model plus per-user offsets ([Aberdeen et al.](https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/36955.pdf)). Tie-strength research found recency of communication and intimacy dominant, with 87.2% strong-versus-weak classification accuracy ([Gilbert & Karahalios](https://collablab.northwestern.edu/CollabolabDistro/nucmc/GilbertKarahalios-PredictingTieStrength-CHI09.pdf)). Field data show fast responses are driven by close relationships and time-critical coordination ([Pielot et al.](https://ic.unicamp.br/~oliveira/doc/MHCI2014_An-in-situ-study-of-mobile-phone-notifications.pdf)). That maps onto a tiered design.

The phone assigns each notification a **class** and a **score from 0 to 100**. Hard classes come first: CALL_INCOMING, ALARM, OTP, SECURITY, PRIORITY_CHAT. These get a score at or above the breakthrough level (80), which can speak alone. Below them, a base score comes from the sender tier (starred or high local affinity, known contact, unknown), the app and channel prior (learned open rate), and content cues (question, direct mention, "urgent", delivery code, money "debited", "collect request"). Penalties apply for ads and promos (-P suffix, `CATEGORY_PROMO`, promo keywords), `FLAG_ONGOING_EVENT`, progress and media categories, group summaries, `isAmbient()`, importance at or below LOW, and `matchesInterruptionFilter()==false`. The user's explicit deny and allow rules override the model entirely, which mirrors Apple's design where user-set choices always beat the inferred ones ([Apple Support](https://support.apple.com/en-ie/guide/mac-help/mchldf5e4cb6)). Security alerts deserve special care: new-device sign-in text, a card debit, "not you", "block card", Google Play Services and the `android` package should be critical, and a bank -T alert with "debited" or "login" should score at the breakthrough level even though it is a bank message.

One tension is worth stating. Alarms and calls already ring on the phone, and the phone's `getLastAudiblyAlertedMillis()` shows the system alerted audibly. VOID should wake for an incoming call mainly when the user is at the Mac and the phone is not obviously ringing nearby, or simply offer "Rahul is calling" as a one-line interrupt. This is a product decision and appears under open questions.

## Interrupt at a breakpoint, with a hard cap, and let pressure build with decay

**Sourced.** Holding an interruption until a task breakpoint reduces cost, but only briefly. In OASIS, notifications were held a mean of **88.6 s** (SD 139.3 s) and 64% landed at moments users agreed were breakpoints; frustration was 2.6 at medium breakpoints versus 4.5 for immediate delivery. Relevant content was far less irritating than irrelevant (3.59 versus 4.98). Crucially, 22 scheduled notifications were never delivered because no breakpoint appeared, which is the argument for a maximum wait ([Iqbal & Bailey, CHI '08](https://www.interruptions.net/literature/Iqbal-CHI08.pdf)). Delivery at detected breakpoints cut cognitive load 46% in a controlled study (N = 37) and 33% in the wild (N = 30) ([Mehrotra & Musolesi survey](https://arxiv.org/pdf/1711.10171)). Predicting receptivity from sensors tops out near 60 to 87% accuracy, and inattention periods typically last only 2 to 5 minutes (same survey), so a deterministic gate should precede any learned timing. Batching three times a day improved attention and stress but raised fear of missing out; hourly batching did little; no notifications at all raised anxiety ([Fitz et al. 2019](https://static1.squarespace.com/static/57a40c19414fb54f51f8095f/t/614a55faa7b89e25f4e48ad1/1632261627146/2019+Fitz+Batching.pdf)). LinkedIn's spacing work found that a send threshold of zero is "greedy and annoying" and that state such as sends in the past 24 hours belongs in the decision ([arXiv 2202.03867](https://arxiv.org/pdf/2202.03867)). Horvitz's framing weighs an item's growing cost of delay against the current cost of interruption ([Microsoft Research](https://www.microsoft.com/en-us/research/publication/attention-sensitive-alerting/)). The notes found **no published half-life, cooldown, debounce or threshold values** for proactive notification speech.

**Design inference.** The mechanism is a pressure score, `P = sum(score_i x 0.5^(age_i / halfLife))`, over unannounced items. Speak when `P` crosses a threshold and the gate is open. Items at or above the breakthrough level skip the threshold but still respect the hard gates (below), except a true emergency class. Debounce new arrivals by 60 to 120 s so a burst of group messages becomes one utterance, matching OASIS's roughly 90 s mean hold. Cap the wait for any item above the speak-worthy floor (for example 10 minutes for medium items, 2 minutes for high) so nothing starves as in OASIS. After speaking, mark every included item as announced so it never counts again, enforce a minimum gap between proactive utterances, and apply a fatigue penalty that scales with utterances in the last few hours. Beyond a per-day budget, roll the remainder into a scheduled digest, in the spirit of the three-times-a-day finding. Because total silence harms (FoMO and anxiety), always keep a pull path: "VOID, anything new?" should read the pending list on demand.

Context gates fall into three groups. **Hard gates, never speak:** an active call or the microphone in use, a calendar meeting in progress, screen sharing or recording, VOID or other media already speaking, a Focus or DND mode that does not allow the sender or app, and quiet hours. **Soft gates, defer to the next breakpoint:** typing within the last few seconds, a full-screen app, video or a presentation. **Presence:** if the Mac is idle several minutes or locked, hold items and summarise on return, or let the phone handle it. These gates come from the Horvitz line of work (conversation, activity and presence inputs) and from Apple's rule that user-set Focus choices override inference, but the notes found no study quantifying screen-share, full-screen or typing-burst gates for spoken alerts, so the specific gates are design choices. One useful sourced caution: silent ringer mode did not slow how fast people checked notifications ([Pielot et al.](https://ic.unicamp.br/~oliveira/doc/MHCI2014_An-in-situ-study-of-mobile-phone-notifications.pdf)), so phone silence is not evidence the user is unavailable. Phone DND state, however, is the user's explicit statement, so VOID should mirror `matchesInterruptionFilter()` and treat a DND-blocked notification as non-wake unless it is in the critical set the user opted in.

## Speak a one-breath headline, hide bodies on speakers, and never let the small model paraphrase claims

**Sourced.** Siri's Announce Notifications is the closest shipped analogue. It announces only when headphones are worn and the device is locked, never while the device is in use; the user can choose Priority, "Time Sensitive and Direct Messages", or All; it plays a tone first, can read a reply back before sending, and stops when an earbud is removed ([Apple Support 102536](https://support.apple.com/102536)). Alexa proactive events are opt-in, expire, are rate-limited per skill (the number is unpublished), and deduplicate by reusing a `referenceId` ([Alexa Proactive Events API](https://developer.Amazon.com/docs/smapi/proactive-events-api.html)). Amazon's length rule is the one-breath test, with two to five items as the ceiling for spoken lists ([Alexa blog](https://developer.amazon.com/blogs/alexa/post/531ffdd7-acf3-43ca-9831-9c375b08afe0/things-every-alexa-skill-should-do-pass-the-one-breath-test)). On the failure side, Apple's summary of a BBC story falsely said Luigi Mangione had shot himself, and Apple paused news and entertainment summaries in iOS 18.3 ([The Decoder](https://the-decoder.com/apple-pauses-ai-generated-news-summaries-after-serious-accuracy-issues-surface/)). They returned in iOS 26 behind an opt-in with a warning that "summarization may change the meaning" ([9to5Mac](https://9to5mac.com/2025/07/22/ios-26-beta-4-re-enables-apple-intelligence-notification-summaries-for-news-apps/)). Google's Android 16 summaries were reported accurate but rarely triggered in a single reviewer's two months ([Android Authority](https://www.androidauthority.com/pixel-10-ai-notification-summaries-two-month-review-3635681)).

**Design inference.** The utterance has four parts: a short earcon, a one-breath headline with counts grouped by person or app ("Three messages: two from Rahul about the deploy, one from Mom"), at most two or three named items with the rest collapsed ("and four more from Slack"), then a single question offering two or three actions ("Hear them, reply, or remind you in an hour?"). Full content is a second step the user requests. Deterministic code should produce the who, which app and how many; the 0.8B model should at most rank items or produce a very short gist marked as such ("roughly:"), and message text should be quoted verbatim and truncated rather than rewritten. News, money, health and security text should be read as written or reduced to sender and app only. On the Mac there is no headphone gate, so use the output route as the privacy switch: if the active output is headphones or AirPods, VOID may read the first line of a message; on built-in or external speakers it speaks sender, app and count only, and for OTPs it says "a code arrived from HDFC" and never the digits. Speech must be interruptible within a few hundred milliseconds by "stop", "quiet" or a hotkey, and "not now" must mark the batch acknowledged. Offered actions should map to what the link can actually do: hear, remind, dismiss (and mark read on the phone), and reply by dictation with a read-back before sending, which copies Siri's confirm step. Replying requires the phone side to fire the notification's reply action; whether each app exposes one is part of the logging task.

## Reminders: absolute-time records, re-checked on every wake, re-evaluated at fire time

**Sourced.** `NSDataDetector` parses many dates but cannot take a custom reference date, and the known workarounds are fragile ([Stack Overflow thread mirror](https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/questions/21244144/set-context-date-for-nsdatadetector)). Dispatch's monotonic clock does not advance during sleep, which pushes fire times out by the sleep duration, while wall-clock deadlines exist as a separate type ([swift-evolution thread](https://lists.swift.org/pipermail/swift-evolution/Week-of-Mon-20160711/024314.html)). Apple DTS advised comparing dates instead of trusting a timer, and one developer found workspace sleep and wake notifications unreliable ([Apple Developer Forums 677029](https://developer.apple.com/forums/thread/677029)). `NSBackgroundActivityScheduler` is documented as suited to low-priority background work ([Apple docs](https://developer.apple.com/documentation/foundation/nsbackgroundactivityscheduler)), so it is wrong for user-visible reminders. ChatGPT Tasks and Gemini Scheduled Actions both cap active schedules at 10 and notify on fire; Gemini prepares content up to an hour before delivery, so it can be stale ([Maginative](https://www.maginative.com/article/openai-launches-scheduled-tasks-in-chatgpt/); [Google Gemini Help](https://support.google.com/gemini/answer/16316416?hl=en-GB)). No source shows an assistant cancelling a reminder because the underlying item was handled elsewhere.

**Design inference: parsing.** Layer three parsers and a fallback. First, a regex for durations ("in 20 minutes", "in an hour", "half an hour") that returns `now + interval`, covering most "remind me about these in 1 hour" requests without any model. Second, a user-editable table of vague periods seeded from the user's routine (morning 09:00, after lunch 14:00, evening 18:00, tonight 20:00, "after gym" at the gym end time), rolling to tomorrow if already past and saying so. Third, `NSDataDetector` for explicit dates and times. Last, the 0.8B model returning only JSON (`relative` minutes or `absolute` ISO) that code validates as parseable, in the future, and within one minute to 30 days; otherwise ask "When should I remind you?". Always speak the resolved absolute time back ("Okay, 3:40, in an hour") because phrases like "at 5" are ambiguous. Which phrases `NSDataDetector` handles on the user's macOS version was not verified and needs a quick test.

**Design inference: scheduling.** Keep a `ReminderStore` as an atomically written JSON file (or SQLite) in Application Support, one record per reminder with `id`, `createdAt`, `fireAt` in UTC, the original phrase, `itemRefs` (notification keys, sender or thread ids), `status`, `snoozeCount` and a late-fire policy. Arm a single wall-clock timer for the earliest pending item, but make the handler re-read the store and fire everything with `fireAt <= now`, so a missed or early timer does no harm. Call the same idempotent `checkDue()` at launch, on `NSWorkspace.didWakeNotification`, on session-active, on `NSSystemClockDidChange`, on time-zone change, on day change, and on a cheap 60-second tick. Add a `UNNotificationRequest` with the same identifier as a backup banner if VOID is not running, and remove it when VOID handles the reminder. Register launch at login through `SMAppService.mainApp` rather than a hand-written plist. If the Mac slept through `fireAt` and wakes within a grace window (about two hours for "in an hour"), fire after a few seconds' settle time and say it was late; beyond that, show it as missed at the next interaction or in the morning digest, and never drop one silently. "In an hour" is stored as an instant; "tomorrow at 9" is stored as local components plus time zone and recomputed on a zone change. Whether a missed UN trigger is delivered after sleep, and whether `Timer(fireAt:)` fires promptly on wake, are unverified, and App Nap behaviour for a menu-bar agent is also unverified.

**Design inference: fire-time behaviour.** Because Gemini's pre-computed content can go stale, compute the follow-up at fire time. For each `itemRef`, check whether the phone notification still exists (the companion can report removals), whether the user replied in that thread, and whether newer messages arrived. If all items are resolved, cancel quietly. Otherwise give a one-breath re-summary of only the open ones and what changed, then offer reply, snooze or done. Offer fixed snoozes (15 or 30 minutes, an hour, this evening) plus free-form times through the same parser. After two or three snoozes change the wording ("You've pushed this twice, want me to drop it?") rather than getting louder. If the user is away, do not speak; post the UN banner and repeat by voice when presence returns. If ignored, re-offer once at the next natural interaction and then mark missed. Cap active reminders at 10 to 20 and support "what reminders do I have", "cancel that" and "move it to 5".

## Learning from reactions: start with rules, add a per-user offset, treat explicit corrections as strong

**Sourced.** Gmail Priority Inbox inferred labels from opens and replies in a window after delivery, weighted manual corrections higher, and combined a global model with per-user log-odds updated online; error fell from 45% (global only) to 38% (user models) to 31% (with per-user thresholds). False negatives ran 3 to 4 times false positives because people open mail they do not consider important ([Aberdeen et al.](https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/36955.pdf)). InterruptMe's online learning stabilised in about a week with 20 users ([survey](https://arxiv.org/pdf/1711.10171)). Learned receptivity models beat users' hand-written rules, and PrefMiner's suggested rules were accepted 56.98% of the time, which supports offering mined rules for confirmation ([survey](https://arxiv.org/pdf/1711.10171)). LinkedIn treated disables as negative reward and used a long-horizon objective to avoid short-term gains that erode engagement ([arXiv 2202.03867](https://arxiv.org/pdf/2202.03867)).

**Design inference.** Log each spoken alert with its features and the outcome. Strong positives: the user replied, asked a follow-up, or said "tell me about X more". Weak positives: opened the phone notification within a few minutes (noisy, per Gmail's lesson). Negatives: "not now", an ignored alert, a dismiss-without-open on the phone, and strong negatives for "stop telling me about X" or disabling a source. Start from the hand-set weights as the global prior, add a per-key offset (per sender, per package-channel) updated by a small online logistic step with strong regularisation toward the prior, and keep a user threshold that moves only on explicit voice corrections. Turn repeated patterns into proposed rules the user confirms ("You've dismissed Swiggy offers nine times. Want me to stop mentioning them?"). Never let learning lower a critical class below its breakthrough floor or override a user rule. Expect a week of data before the offsets mean anything, and do not attempt a bandit until there are hundreds of labelled alerts.

## Conclusion

The main shift in understanding is that this is mostly a gating problem, not a scoring problem. The sourced evidence supports short holds, hard caps and rare digests far better than it supports any particular weight, and the sharpest unknowns are about the Android side: what the phone actually delivers once Android 15's redaction and restricted settings are in play. Build the logger and the deterministic classes first, ship conservative defaults (breakthrough classes plus priority people only), and let measured behaviour decide whether the pressure model ever needs to fire on ordinary items.

A second implication is that the reminder system is the pressure valve for the whole design. If "remind me in an hour" is cheap, accurate and trustworthy, VOID can afford to stay quiet more often, because deferral is no longer loss. That makes reminder correctness (restart-safe, sleep-safe, and re-checked against live state) a precondition for turning proactive speech up.

## Phased implementation plan

All numbers in this plan are **starting values to tune, not researched facts**. Nothing in the sourced notes publishes weights, half-lives or thresholds.

### Phase 0: capture before building (Android, about 1 to 3 days of use)

Add `NotificationLogService extends NotificationListenerService` and `LogStore` (append-only JSON lines in app storage, exportable). On each `onNotificationPosted`, `onNotificationRemoved` and `onNotificationRankingUpdate`, dump: package, `sbn.key`, post time, `category`, `channelId`, flags, `template`, `shortcutId`, `extras` keys and the text values, `EXTRA_PEOPLE_LIST`, messaging `Person` fields (key, uri, isImportant, isBot), the full `Ranking` (importance, `isConversation`, `isImportantConversation`, `isAmbient`, `matchesInterruptionFilter`, `userSentiment`, `hasUserSetImportance`, smart actions and replies, last audible alert), whether a reply action exists, and `fullScreenIntent` presence. Also handle SMS: capture sender headers and bodies through the notification and, if permitted, `READ_SMS`, to compare. Validate these specific assumptions: the exact redacted OTP string and whether title or sender is also redacted; whether granting `RECEIVE_SENSITIVE_NOTIFICATIONS` via ADB appops works on the user's phone; how WhatsApp, Telegram, Gmail, GPay, PhonePe, Paytm, Swiggy, Zomato, Amazon, the dialer, the clock and Google Play Services fill category, channel and Person fields; whether starred and priority-conversation flags are visible; whether Hinglish bank SMS is redacted; what the phone OEM is and whether it has Android's classification or organiser; which phrases `NSDataDetector` parses on the Mac; whether `Timer`/UN triggers fire after sleep; and whether the Mac's active output route can be read reliably. Install note: allow restricted settings in App info before enabling Notification access on a sideloaded APK.

### Phase 1: Android classification and link (Java)

Classes to add: `NotificationScorer` (computes class and score), `SenderTier` (starred and local affinity lookup, cached), `SmsHeaderParser` (the TRAI regex and suffix), `OtpDetector` (regex plus redaction placeholder check), `ChannelStats` (per package-channel open and dismiss counts), `DedupeCache` (key plus content hash), and `LinkClient` (existing link, extended). Permissions: `READ_CONTACTS`, optionally `READ_CALL_LOG` and `READ_SMS`.

Fields sent per event over the existing link (suggested names):

| Field | Meaning |
|---|---|
| `id`, `key`, `pkg`, `channelId`, `postTime` | identity and dedupe |
| `class` | CALL_INCOMING, ALARM, OTP, SECURITY, PRIORITY_CHAT, CHAT, PERSONAL_SMS, TXN_SMS, SERVICE, PROMO, ONGOING, OTHER |
| `score` | 0 to 100 from the phone |
| `sender` (display name only), `senderKey`, `senderTier` | who, never the number unless needed |
| `title`, `bodySnippet` (max 120 chars), `bodyRedacted` (bool) | content; omit body for OTP/security-class by default |
| `isGroup`, `isConversation`, `isImportantConversation`, `dndAllowed` | system signals |
| `smsSuffix` (P/S/T/G/none) | India header |
| `removed` (event type), `replyable` | for fire-time checks and reply actions |

Default weights (starting values): priority conversation 85; call incoming 90; alarm 80; OTP 80 (speak "code arrived" only); security 90; starred sender message 70; known contact message 50; unknown personal SMS 35; -G 45; -S 30; -T non-OTP non-security 40; -P 3; promo category 3; ongoing/progress/media/group-summary 0; per-app prior added from -10 to +10. Modifiers: question mark or direct mention +10; urgency words +10; promo keywords -25; `isAmbient` or importance <= LOW -30; `dndAllowed` false -40 (non-critical only).

### Phase 2: Mac pressure engine and gates (Swift)

Files and types to add: `NotificationInbox` (receives link events, dedupes, stores pending), `PressureEngine` (decayed sum, thresholds, debounce, caps), `ContextGate` (call/mic, calendar meeting, screen sharing, Focus, quiet hours, typing, full-screen, idle/lock, VOID speaking), `PresenceMonitor`, `SpeechPlanner` (headline builder, privacy by output route), `AudioRouteMonitor`, `AnnouncementLog` (SQLite, for learning), and `UserRules` (allow/deny, per-app mute, quiet hours).

Defaults (starting values): breakthrough score 80; speak threshold P = 100; decay half-life 20 min; debounce 90 s (60 to 120 s); minimum gap between proactive utterances 5 min; maximum wait 2 min for score >= 60, 10 min for 40 to 59, otherwise digest-only; fatigue penalty +10 to the threshold per utterance in the last 2 hours; daily proactive budget 8; digest times 09:00, 15:00 and 21:00; quiet hours 23:00 to 08:00 (user's choice); idle threshold 5 min; typing soft gate 8 s; hard gates as listed above. Critical classes bypass the threshold but not hard gates, except incoming calls and security alerts if the user opts them past quiet hours.

### Phase 3: speech, actions and reminders (Swift, plus small Java handlers)

Mac: `Announcer` (earcon, headline, question, stop handling), `IntentRouter` additions for hear, reply, remind, dismiss, snooze, mute app; `ReminderParser` (duration regex, vague-period table, `NSDataDetector`, LLM JSON fallback with validation), `ReminderStore` (JSON in Application Support), `ReminderScheduler` (wall-clock timer, idempotent `checkDue()` on launch, wake, session-active, clock change, time-zone change, day change, 60 s tick), a UN-notification backup, `SMAppService.mainApp` registration, and `ReminderFollowUp` (live re-check, re-summary, snooze ladder). Defaults: grace window 2 h; settle delay after wake 5 s; max 15 active reminders; snooze options 15 min, 30 min, 1 h, this evening; re-wording after 2 snoozes; one re-offer if ignored. Android: `NotificationActionExecutor` (dismiss, mark read, fire the reply action with text) and a `StateQuery` handler so the Mac can ask whether a key is still present or replied.

### Phase 4: learning

Mac: `FeedbackRecorder`, `OffsetModel` (per sender and per package-channel logistic offsets, strong regularisation, floors for critical classes), `RuleSuggester` (mined "stop mentioning X" proposals the user confirms), and a weekly review log. Starting values: learning rate small enough that a single event moves a score under 5 points; strong negative event -15, weak positive +2, strong positive +8; enable offsets only after about 50 labelled alerts. Re-check thresholds after the first week of data.

### Open questions for the user

1. What phone and Android version/OEM are you on, and is it Samsung or Xiaomi rather than Pixel? This decides redaction and organiser behaviour.
2. Are you willing to run the ADB appops grant (or turn off Enhanced notifications) so OTP content can be seen, or should VOID only say "a code arrived"?
3. Should incoming calls and alarms wake VOID at all, given the phone already rings, or only when you are at the Mac?
4. Which contacts count as "close": starred only, or also a list you give VOID by name, and which WhatsApp chats?
5. What are your quiet hours, digest times and acceptable daily proactive count?
6. Do you use headphones at the Mac often enough that a headphone-only body-reading rule is useful, or should bodies never be spoken on speakers?
7. Are you comfortable granting `READ_SMS` and `READ_CALL_LOG` to the sideloaded companion app for affinity and OTP detection?
8. Should security alerts and bank debits be allowed to break through quiet hours?
9. Which apps should never be announced (for example promo-heavy shopping or delivery apps) and which should always be (for example UPI money received)?
10. How much do you want VOID to reply by voice: dictate-and-read-back only, or also canned replies?
