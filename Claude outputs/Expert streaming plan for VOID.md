# Streaming experts on 8 GB: measure first

**VOID can plausibly run a larger-than-RAM Mixture-of-Experts (MoE) model by streaming routed experts from the SSD, but no source has measured this on an 8 GB Mac, so the plan must be gated on three cheap measurements before any Swift is written.** The technique is simple: keep attention, router, embeddings and shared weights resident, and `pread` only the 4-8 experts each layer routes to. Every credible implementation converges on the same recipe (fixed-size contiguous expert records, parallel large `pread`, a small pinned or LRU cache), and every one reports that bytes read per token, not compute, sets the speed. The best first target is **LFM2.5-8B-A1B** (4.76 GB at 4-bit, 0.31 GB resident, about 545 MB of expert reads per token), where my model predicts roughly **9-15 tok/s at 2.5-3.3 GB/s SSD and a 25-40% miss rate**; Qwen3-30B-A3B (17 GB, about 1 GB per token) lands at about 5-8 tok/s only if the miss rate stays near 25%, and at 3-5 tok/s otherwise. The measured Mac evidence is on 36-128 GB machines, the base M3's SSD is about 3.3 GB/s on the 512 GB model but unmeasured on VOID's own drive, and the key published negative result (Flash-MoE: the OS page cache beats a custom cache) was obtained with about 35 GB of free page cache that an 8 GB Mac does not have. The recommended minimal first version is a Swift `StreamingSwitchGLU` with a fixed slot pool per layer, a pre-stacked per-expert file, usage-calibrated pinning, no predictor and decode-only streaming, preceded by a Python routing-trace and cache-simulation stage with explicit go/no-go thresholds.

## Every working system reads experts the same way, and every Mac result sits on a bigger machine

Flash-MoE is the best-documented Apple Silicon design. It streams Qwen3.5-397B-A17B (209 GB) from SSD on a 48 GB M3 Max at **4.36 tok/s** at 4-bit, with a per-layer file where each expert is a fixed 7,077,888-byte block, parallel `pread` of the four active experts, and no custom cache ([Flash-MoE README](https://github.com/danveloper/flash-moe/blob/main/README.md), [repack_experts.py](https://github.com/danveloper/flash-moe/blob/main/repack_experts.py)). Its 58-experiment log is the most useful negative-results record: `mmap` of expert files ran at 0.56 tok/s (five times slower, 240 page faults per expert), `dispatch_io` lost 70%, LZ4 expert compression lost 13%, and `F_RDADVISE` prefetch cut I/O time 31% but raised GPU wait 73% because SSD DMA and GPU compute share one memory controller ([io-and-gpu-exploration.md](https://github.com/danveloper/flash-moe/blob/main/docs/io-and-gpu-exploration.md)). Temporal expert prediction scored a 25% hit rate and cost 18%; an MLP predictor reached 31% accuracy; speculative early routing cost 38% ([results.tsv](https://github.com/danveloper/flash-moe/blob/main/results.tsv)). The headline finding is that deleting a 9.8 GB Metal LRU cache raised throughput from 2.24-3.14 to 5.74 tok/s (2-bit), because wired Metal buffers shrank the OS page cache that was already reaching about 71% hits.

Colibri, the project that prompted this study, reaches the same I/O primitive from C: one `pread` per expert (gate, up and down read as one range when file-adjacent), a per-layer LRU, and a pinned "hot set" seeded from a persisted usage file, with a memory budget that always reserves 2.5 GB for the OS page cache ([colibri.c](https://github.com/JustVugg/colibri/blob/main/c/colibri.c), [ENVIRONMENT.md](https://github.com/JustVugg/colibri/blob/main/docs/ENVIRONMENT.md)). A code comment records that starving the page cache dropped buffered `pread` from about 800 to 180 MB/s on Linux. Colibri's prefetcher ("PILOT") runs the next layer's router on the current layer's stale state and reports 71.6-75.8% recall on GLM-5.2; the same file states both numbers, which is an internal inconsistency, and I found no Colibri measurement isolating PILOT's tok/s gain on a Mac. Colibri is also not an 8 GB Mac tool: its table lists Qwen3.6-35B-A3B at 10 GB minimum and 20 GB measured, and its Mac speeds are 0.3-2 tok/s for GLM-5.2 on 96-128 GB machines ([README](https://github.com/JustVugg/colibri/blob/main/README.md), [metal.md](https://github.com/JustVugg/colibri/blob/main/docs/metal.md)). Issue 379 is the conflict that matters: on an M5 Max with 14-20 GB/s NVMe, growing Colibri's own cache from 1 to 16 slots per layer raised the hit rate from 2.4% to 46.6% yet *slowed* decode from about 2.0 to 1.52 tok/s, because every resident-pool hit paid a Metal residency cost (0.43 ms per resident expert) while a page-cache miss was cheap. The maintainers' fix was a minimal-cache default plus an opt-in `MTLResidencySet`, and they note that on a slow disk (about 80 ms per miss) the cache is essential ([Issue 379](https://github.com/JustVugg/colibri/issues/379)). That caveat is exactly why the Flash-MoE and Colibri findings cannot be transplanted: both say a cache is harmful when the disk is very fast and RAM is plentiful, and VOID has neither condition.

The llama.cpp prototypes supply the slot-pool design and the only sub-32 GB Apple Silicon numbers. Discussion 23324 gives each layer N expert slots in shared memory; a Metal kernel publishes the routed IDs, a CPU sidecar thread does LRU assignment and `pread`, and an `MTLSharedEvent` releases the GPU, which then runs `MUL_MAT_ID` unchanged on the compact pool with exact outputs. On a 36 GB M3 Pro, Qwen3-30B-A3B Q6_K ran 38.1 tok/s fully resident, 27.5 with 64 slots (16.1 GiB wired), 15.7 with 16 slots (7.8 GiB) and 12 with 8 slots (6.3 GiB), and the author later reported about 13 tok/s on a 16 GB M1 Pro ([Discussion 23324](https://github.com/ggml-org/llama.cpp/discussions/23324)). Because the model otherwise fit in RAM there, these numbers measure slot-pool overhead, not SSD-bound speed. Discussion 27149 is the CPU-only 8-16 GB variant: it measured 2.97 GB/s sequential and 6.06 GB/s double-buffered reads on a 16 GB M1, and found GGUF's interleaved layout faults 6,912 pages per expert (111x amplification) versus 192 after an expert-contiguous repack. Its 4.7 tok/s uses simulated compute, its real Accelerate benchmark capped at about 4.4 tok/s, and its pinning data (random 6% hits, text-calibrated 42%, calibrated plus LRU 56%, oracle 88%) came from a 10-token calibration ([Discussion 27149](https://github.com/ggml-org/llama.cpp/discussions/27149)). Neither discussion is merged, and I read no maintainer reply in either.

The MLX-side projects are the weakest evidence. SwiftLM's `--stream-experts` reports 14.1 tok/s for Qwen3.6-35B-A3B-4bit (21.6 GB) at 6.8 GB peak on a 32 GB Mac mini, but a secondary review found its SSD-bytes metric stayed at zero, implying the page cache served the reads, and its source lives in forks of mlx and mlx-swift that I could not read ([SwiftLM README](https://github.com/SharpAI/SwiftLM/blob/main/README.md), [lilting.ch review](https://lilting.ch/en/articles/swiftlm-turboquant-metal-ssd-expert-streaming)). MLX-Flash replaces `QuantizedSwitchLinear` with a cached version and a GPU lookup table, but missing experts get a score of zero and the rest are renormalised, so outputs differ from the real model; its README requires 16 GB or more and its headline "82 tok/s" baseline was a swapping Ollama on a 36 GB machine ([expert_streaming.py](https://github.com/szibis/MLX-Flash/blob/main/mlx_flash_compress/expert_streaming.py), [honest-benchmarks.md](https://github.com/szibis/MLX-Flash/blob/main/docs/honest-benchmarks.md)). An unreviewed mlx-lm post reports 15.0 tok/s for Qwen3.6-35B-A3B on a 16 GB M5 Air with 1.7 GB of MLX memory and byte-identical output, and explicitly calls its 8 GB figures an estimate ([mlx-lm discussion 1940](https://github.com/ml-explore/mlx-lm/discussions/1940)). Treat all of these as **vendor or self-reported, none verified on 8 GB**.

## Routing locality is moderate, so the cache hit rate is the unmeasured variable that decides everything

Academic offloading work targets GPUs with PCIe links (12-32 GB/s), so its speedups do not transfer to a 3 GB/s SSD, and most are relative to naive baselines. Over a tuned LRU the gains are small: ProMoE's learned prefetcher beat llama.cpp's LRU by only 1.09x on average in decode, and on Mixtral (25% of experts active) a trivial baseline beat it ([ProMoE](https://arxiv.org/html/2410.22134v3)). The closest published setup to VOID is FlashMoE (2026), which keeps experts on a 7.4 GB/s NVMe with about 1 GB of RAM free and tests OLMoE-1B-7B and Qwen3-30B-A3B; its learned cache policy beat LRU by roughly 22% throughput on OLMoE and 7% on Qwen3-30B-A3B, though its text is inconsistent on the hit-rate gain (up to 21% in the body, 51% in the abstract) and absolute tokens per second are only in figures ([FlashMoE](https://arxiv.org/html/2601.17063v1)). A separate 2026 negative-result paper on Qwen3-235B-A22B with an 8 GB GPU and a 2.4 GB/s NVMe measured 0.441 tok/s warm and 0.128 cold, and its simple bandwidth model overestimated the cold case by about 1.5x (0.20 predicted), which is why my tok/s tables below carry a derate ([arXiv 2608.18261](https://arxiv.org/pdf/2608.18261)).

The same paper provides the only per-layer locality statistics for a model on our list. On Qwen3-30B-A3B, layer 24, code domain, the next token reuses the same expert 44.4% of the time (22.3% by chance), 52.5% of experts carry 95% of traffic, and a per-layer cache holding 13.4% of experts hits 65.9% under LRU, 60.1% under LFU, 59.2% under static pinning and 79.1% under the Belady oracle. This is a single layer and a single domain, and code-domain experts overlap other domains only 0.11-0.16, so a conversational voice workload could be more or less concentrated. A 20-model study found that most models balance cache effectiveness at about twice the active-expert count per layer, and that models with all-MoE layers and no shared experts are the most consistent ([arXiv 2505.16056](https://arxiv.org/html/2505.16056v1)). Cross-layer prediction accuracy is high for coarse models (about 96% next-layer for 8-16 expert Mixtral and Phi-MoE per [HOBBIT](https://arxiv.org/html/2411.01433v2)) and lower for finer ones (84.7% for ProMoE's learned predictor on 64-expert models). Nothing reports locality for LFM2.5-8B-A1B, OLMoE or Qwen3.5/3.6, and nothing measures conversational speech workloads, so my planning range of 65-80% hits at a 25% cache is an extrapolation from one layer. The Flash-MoE and Colibri evidence also says prediction is the wrong first investment: with I/O at 100+ ms per token and compute near 20 ms, prefetch can hide at most the compute share, and unified-memory contention erased the gain in Flash-MoE's Mac test.

LFM2.5 wins on three grounds. Its 6.2 MB experts are large enough for efficient sequential reads, and 22 layers means only 22 router syncs per token versus 48 for Qwen3-30B. The whole model is 4.76 GB, so it can also be run *non-streamed* as an exact baseline for A/B testing, and with a 1-1.5 GB cache budget it would hold roughly 160-240 of its 704 experts (23-34%). The honest consequence is that LFM2.5 is a model that nearly fits: streaming is a safety valve that frees 3-4 GB for ASR, TTS and the reflex model, not a way to reach a much larger model. Its weaknesses are no Hindi in its documented language list, a reasoning-tuned default that needs thinking suppressed for voice, and a license to read before freelance use. Qwen3-30B-A3B is the real "larger than RAM" test, since it is 17 GB and only 5% resident-friendly, but it needs about 1 GB of expert reads per token and 384 sync points; I rank it second and gate it on LFM2.5 succeeding. Published tok/s on base 8-16 GB Macs for any of these is essentially absent: the only figure I found is a calculator estimate of about 97 tok/s for LFM2.5 on a 16 GB M1 Pro, explicitly "estimated from fit model" ([willitrunai](https://willitrunai.com/de/can-run/lfm2.5-8b-a1b-on-m1-pro-16gb)), which I discard.

## The M3's SSD is probably about 3 GB/s, and the 8 GB page cache is too small to trust Flash-MoE's lesson

The only base-M3 14" figure found is a Blackmagic result of **3,320 MB/s read** for the 512 GB model, while the 512 GB M3 Pro reads about 5,260 MB/s and 1 TB machines about 4.9 GB/s ([Mac4ever](https://www.mac4ever.com/mac/179994-test-des-debits-ssd-des-macbook-pro-m3-m3-pro-et-m3-max), [MacRumors](https://forums.macrumors.com/threads/ssd-speeds-of-m3-macbook-pro.2410262)). A forum poster guessed 2.9 GB/s for the base M3, an unmeasured guess that is close but not independent. Queue depth matters: on a Mac Studio, sequential read was 2.9 GB/s at queue depth 1 and 6.7 GB/s at depth 8 ([Eclectic Light](https://eclecticlight.co/2022/04/22/what-performance-to-expect-from-ssds/)), which is why every precedent issues 4-24 concurrent reads. No review reports random-read throughput at 1-8 MB on the base M3, so my planning value of **2.0-3.0 GB/s for 1-6 MB reads at depth 4-8** is an estimate. Flash-MoE's 17.5 GB/s "SSD" reading is almost certainly cache-assisted and must not be used; any benchmark that rereads the same file measures RAM.

The memory budget is the second constraint, and every number in it is an assumption. With macOS at 2.5-3.0 GB, the reflex model at 0.6-0.7 GB, ASR plus TTS at 0.5-1.0 GB, the VOID app and KV at 0.5-1.0 GB and Chrome for the music tool at 1-2 GB, roughly **0-2.7 GB remains, about 1.5 GB in the middle case**. That budget has to cover both a pinned expert pool and the page cache that serves non-pinned reads, so the cache design question reverses relative to Flash-MoE. Flash-MoE's result (page cache beats app cache) depended on about 35 GB of free page cache and a 17.5 GB/s drive; Colibri's #379 fix likewise assumed a 14-20 GB/s disk where a miss is cheap. On an 8 GB machine with a 3 GB/s drive, a miss costs about 2 ms per 6 MB expert and the page cache will hold little, so a small, deliberately sized, calibration-pinned pool is more likely to win. This is an untested inference; the plan below makes it Experiment 4. Two supporting facts: MLX does not mmap safetensors (it reads into allocator memory), and an upstream mmap proposal was declined by a maintainer ([MLX PR 4249](https://github.com/ml-explore/mlx/pull/4249)), while the PR's author reports Metal wires the whole buffer on first use. So the "let the OS cache it" trick has to happen outside MLX arrays: `pread` from a file the kernel caches, into slot buffers MLX owns, at the cost of double residency for hot bytes.

## Implementation: a Swift slot pool inside mlx-swift-lm, with a Python sandbox ahead of it

Reading mlx-swift-lm 3.32.3 shows a clean hook. LFM2MoE, Qwen3MoE, OlmoE and Qwen3.5-MoE all build a public `open class SwitchGLU` whose experts are stacked `[numExperts, out, in]` tensors consumed by one `MLX.gatherQuantizedMM` call, so a `StreamingSwitchGLU` subclass can be swapped in after construction using the same module-replacement mechanism that `quantize(model:)` uses, with no fork of model files ([SwitchLayers.swift](https://github.com/ml-explore/mlx-swift-lm/blob/3.32.3/Libraries/MLXLMCommon/SwitchLayers.swift)). GPT-OSS is the exception (a private `SwiGLUSwitchGLU`), and Qwen3.5 decode runs through compiled traces that cannot contain a mid-graph CPU sync, so both stay off the streaming path. The stock `loadWeights` ends in `eval(model)`, which reads every expert byte into RAM, so a custom loader that materialises only non-expert tensors and keeps a per-(layer, expert) offset table from the safetensors header is mandatory ([Load.swift](https://github.com/ml-explore/mlx-swift-lm/blob/3.32.3/Libraries/MLXLMCommon/Load.swift)). `gather_qmm` derives the expert count from the weight tensor's shape at eval time and requires `uint32` indices, so a smaller per-layer slot tensor `[S, out, in]` plus remapped indices keeps shapes static and avoids recompilation ([MLX quantized.cpp](https://github.com/ml-explore/mlx/blob/1f8e74e3f12f31365464a6867c6579f0e9b29d85/mlx/backend/metal/quantized.cpp)).

The per-layer flow is: compute the router indices, `eval` them and read them on the CPU (one GPU-to-CPU sync per MoE layer, 22 per LFM2.5 token), map each routed expert to a slot (pinned set first, then LRU), `pread` misses into slot storage with 4-8 concurrent reads, build the `uint32` slot-index array and call the unchanged gather. Three details carry risk. First, `MLXArray` has no public no-copy constructor from a pointer, so filling slots means either writing into an evaluated array's shared-mode storage (an unsupported hack that violates array immutability, and unverified across `Memory.clearCache()`), or building fresh `[k, out, in]` arrays per token at the price of a copy. Second, the sync cost is unmeasured on the M3: SwiftLM cut evaluations per token from about 1,400 to 48 by batching, and the llama.cpp design avoided CPU round-trips entirely with a shared event that MLX does not expose. Third, prefill touches most experts per layer (the `doSort` path at 64 or more indices wants the full tensor), so prefill needs a separate layer-wise path that loads each layer once per large chunk, or the streamer is decode-only and prompt processing runs with generous chunking. I rate this option at 8-12 engineer-days with medium risk; an SwiftLM-style fork of mlx with custom Metal kernels is 15-30 days with high maintenance risk and is not recommended ([SwiftLM README](https://github.com/SharpAI/SwiftLM)).

The alternatives are weaker. Embedding llama.cpp via the `llama.swift` XCFramework is cheap to start, but on Metal its mmap path wraps whole regions in wired buffers, so genuine demand paging works only when expert tensors are forced to the CPU backend through `tensor_buft_overrides` (the C form of `--n-cpu-moe`), which on an 8 GB M3 means CPU-bound speeds near the 4.4 tok/s ceiling that the 16 GB M1 prototype measured, with swap-thrash risk and a second inference stack with its own KV cache, templating and Metal budget ([llama.swift](https://github.com/mattt/llama.swift), [issue 19825](https://github.com/ggml-org/llama.cpp/issues/19825)). It is the cheapest *measurement* (hours) and a sensible control, not the product. A Python mlx-lm sidecar running MLX-Flash or a hand-patched `switch_layers.py` is the fastest way to learn the answer on this exact Mac (1-3 days), but shipping it inside a Swift app means managing a Python runtime and process, and MLX-Flash's approximate fallback changes outputs. The recommended hybrid is therefore sequencing, not coexistence: Python for traces and simulation, llama.cpp CPU-experts as a baseline measurement, and Swift for the product.

## A staged plan with numeric gates

Stage 0 (half a day) measures the platform and costs nothing in code. Print `MTLDevice.recommendedMaxWorkingSetSize` (the 5.3 GB and 6 GB figures in circulation are unverified), run a `pread` benchmark over a file larger than RAM using 1, 2, 4 and 6 MB reads at depth 1, 4, 8 and 16 with and without `F_NOCACHE`, and time a forced `eval(indices)` plus `asArray` sync inside the stock LFM2MoE forward pass. **Gate 0:** continue only if sustained random 4-6 MB read bandwidth is at least 2.0 GB/s at depth 8 and the per-layer sync adds no more than about 1 ms (about 22 ms per token for LFM2.5). Below that, stop and keep the dense models from the earlier VOID report.

Stage 1 (1-2 days, Python mlx-lm) records the routing trace: per token and layer, the selected experts, on VOID's own prompts (voice dialogue, tool calls, music requests, short answers of 20-60 tokens) with thinking off. **Gate 1:** from the trace compute per-layer unique experts per token and next-token reuse; proceed if next-token reuse is clearly above chance (Qwen3-30B's 44% against 22% is the reference) and the working set of a typical 10-turn session is below roughly 60% of experts. If routing looks near-uniform, no cache will help and the model should be run only if it fits.

Stage 2 (1-2 days) simulates policies offline on those traces: LRU, LFU, static pinning calibrated on a held-out sample, calibrated pin plus LRU, and the Belady oracle, across slot counts of 8, 16, 24, 32 and 48 per layer (and shared-budget variants), reporting miss rate and bytes per token, including cold-start cost and cross-session persistence of the usage file. **Gate 2:** at the budget VOID can actually spare (1-1.5 GB), the best realistic policy must reach a miss rate at or below about 0.35 for LFM2.5 (about 190 MB per token) or 0.25 for Qwen3-30B (about 255 MB); the tok/s model below turns this into a prediction, and Gate 2 passes if predicted decode is at least 8 tok/s with the 1.5x derate applied. Also run the llama.cpp CPU-experts control here on the same GGUF quant, with `vm_stat` swap counters, so the Swift prototype has a measured competitor.

Stage 3 (8-12 days) builds the Swift prototype for LFM2.5 only: custom loader, `StreamingSwitchGLU`, `pread` pool, fixed slots, calibrated pins, decode only, with a feature flag that falls back to stock `SwitchGLU`. **Gate 3:** greedy output must match the stock model token for token (the design is exact), decode must reach at least 8 tok/s sustained over a five-minute run with no swap growth and green memory pressure while ASR, TTS and the reflex model are resident, and time to first token for a short prompt must stay under about 1.5 s. Only then consider OLMoE as a second architecture, Qwen3-30B as a stretch, and (Stage 4) prefetching from the previous token's same-layer experts or Colibri's resident-only two-step predictor, justified only if measured I/O wait exceeds compute.

The throughput model is `t = m x X / BW + t_compute + t_sync`, where X is expert bytes per token, m the miss rate, and BW the effective read bandwidth. I assumed fixed costs (compute plus sync) of 26 ms for LFM2.5 (about 15 ms of GPU work and 22 syncs at about 0.5 ms), 20 ms for OLMoE, 44 ms for Qwen3-30B (48 syncs) and 45 ms for Qwen3.6, all unmeasured guesses that Stage 0 replaces. No overlap is assumed, which matches Flash-MoE's finding that SSD and GPU work do not overlap profitably on unified memory.

For a voice reply the target is a sustained rate above about 5 tok/s to stay ahead of speech, which LFM2.5 meets across most of the table and Qwen3-30B meets only at miss rates of 25% or less on a fast drive.

## Risks, and the smallest version worth building

Thermal behaviour is unmeasured: the 14" has a fan and Oakley saw no SSD throttling on M1 Pro/Max drives, but there is no sustained-read thermal or power data for a base M3 doing SSD DMA plus GPU decode, so the Stage 3 five-minute run is the first evidence. Memory pressure is the larger operational risk: the streaming pool and the page cache share one pool with macOS, ASR, TTS and the reflex model, a wired slot pool cannot be reclaimed (the #379 and Flash-MoE lesson), and the 10.67 GiB practical limit one author hit on a 16 GB Mac for gpt-oss suggests a proportionally tight ceiling here. The design should therefore size slots from `os_proc_available_memory`-style headroom checks at load, keep a hard cap, shrink the pool when the music tool or a browser opens, and expose a stock-path fallback. SSD wear is a lesser concern because reads do not consume program-erase cycles; the exposure is swap writes if the footprint overshoots, so log `vm.swapusage` and swap-outs during every benchmark and make a non-zero growth a fail condition. A runaway local LLM exhausting memory reportedly corrupted an APFS volume on a Mac mini ([DEV](https://dev.to/hexisteme/the-guardrail-has-to-be-code-how-a-runaway-local-llm-corrupted-apfs-and-bricked-a-mac-mini-4780)); I read only the headline, but the lesson, that guardrails belong in code, applies. Two further correctness hazards are speculative decoding, which SwiftLM's PR notes hurts streaming because each verified position routes to different experts, and low-bit experts, since 2-bit broke JSON in Flash-MoE's 397B and 3-bit broke gpt-oss quality in a 16 GB Mac report, so 4-bit is the floor. Approximate substitutions (MLX-Flash's zero-score fallback, Colibri's `CACHE_ROUTE`, HOBBIT-style low-precision fallbacks) change outputs and should be excluded from v1.

The recommended minimal first version is therefore: LFM2.5-8B-A1B 4-bit, repacked offline into one contiguous 6.2 MB record per (layer, expert) in a single file 16 KB-aligned, non-expert tensors loaded normally (about 0.3 GB), a fixed 8-12 slots per MoE layer (about 1.1-1.6 GB at 6.2 MB per slot across 22 layers) filled first from a usage-calibrated pinned set and then LRU, four to eight concurrent `pread`s per layer, one router sync per layer, decode-only streaming with prompts limited to short chunks, exact outputs, a one-line fallback to the stock model when the memory check says the full 4.76 GB fits, and a trace logger that persists the usage file across sessions. Nothing about prediction, prefetch, a second model architecture, Qwen3.5's compiled path or GPT-OSS belongs in version one.

## Conclusion

The combined evidence reverses the usual framing. On this machine the interesting result is not that a 30B model might squeeze in, but that the best-supported target, LFM2.5, nearly fits already, so streaming's first job is to give back 3-4 GB of RAM to the rest of VOID at a modest speed cost, and the stretch to Qwen3-30B is gated on a miss rate that nobody has measured for any conversational workload. The two most-cited rules from big-Mac projects, "trust the OS page cache" and "caches make things slower", are conditional on abundant RAM and a 14-20 GB/s disk, and the 8 GB regime sits on the other side of both conditions; the first experiment that matters is therefore a head-to-head of a small calibrated slot pool against page-cache-only reads on the actual machine.

Because the decision is cheap to falsify, the plan front-loads falsification: three half-day measurements and a trace-driven simulation decide whether the 8-12 day Swift build is worth starting. If Gate 0 or Gate 2 fails, the earlier recommendation holds unchanged (a dense 4B plus a small reflex model), and the work has cost about a week. If they pass, VOID gains a measured, exact, fork-free expert-streaming path that also gives a quantified answer to whether bigger MoE models are worth chasing on 8 GB.
