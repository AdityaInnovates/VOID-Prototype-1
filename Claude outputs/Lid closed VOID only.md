# Keeping VOID alive under a closed lid

A MacBook Pro 14" M3 can run VOID with the lid closed, but only by keeping the whole machine awake. macOS has no supported "this app stays awake while everything else sleeps" mode, so "VOID only" can be approximated but never achieved literally. The practical recipe is to keep the system awake with `pmset disablesleep` (what VOID already does) or with true clamshell mode (AC power, an external display or dummy plug, and external input), then shrink everything else's footprint. Lid close is a "forced sleep" that assertions such as `caffeinate` cannot stop, only delay ([Apple QA1340](https://developer.apple.com/library/archive/qa/qa1340/_index.html)). The built-in microphone is disconnected in hardware when the lid closes ([Apple Platform Security](https://support.apple.com/guide/security/secbbd20b00b/web)), so VOID must take voice from the Android phone link or an external mic, and must pin that input device. Freezing other apps with SIGSTOP is feasible but of limited value. It cuts CPU, not RAM, which is the scarcer resource on an 8 GB machine. It also carries a real risk of leaving apps stuck unless an independent watchdog exists. The main hazards are heat, because the closed lid reduces cooling, and an unattended "never sleeps" flag, so the design should add a thermal and battery guard. Nothing in the evidence was measured on an M3 14" or on macOS 26.4 or later, so the key claims below need a short on-device test.

## Selective per-app awake does not exist, so the goal becomes a quiet whole-system awake

System sleep on macOS is global. Power assertions are a system-wide veto, not per-process isolation. Apple documents Power Nap and Dark Wake as short, system-initiated maintenance wakes. On battery they check Mail, update Calendar and refresh iCloud, and on a power adapter they also run software updates and Time Machine ([Apple Mac User Guide](https://support.apple.com/en-us/guide/mac-help/mh40774/15.0/mac/15.0)). Apple's engineers say DarkWake has no public API, cannot be opted out of by apps, and ends in Maintenance Sleep within about a minute in the posted log ([Apple Developer Forums](https://developer.apple.com/forums/thread/770517)). A long-running MLX process therefore cannot ride through those windows, because processes freeze whenever the system sleeps. The nearest approximation is to keep the system awake, turn the display off, and minimise other activity. This is the framing VOID's feature should present to the user. The goal is a quiet machine, not an isolated one.

Lid close itself resists the usual tools. QA1340 states that "even with I/O Kit, it is not possible to prevent forced sleep, only delay it". That is why `caffeinate -i`, `-d` and `-s` do not hold a lid-closed MacBook awake without an external display. The man page also notes that `-s` is valid only on AC power ([caffeinate(8)](https://keith.github.io/xcode-man-pages/caffeinate.8.html)). One forum user ran `sudo caffeinate -dimsu` plus an Amphetamine patch and the Mac still slept on lid close ([Apple Community](https://discussions.apple.com/thread/255092461)). KeepingYouAwake, a `caffeinate` wrapper, says outright that it only works on laptops with an open lid ([KeepingYouAwake](https://github.com/newmarcel/KeepingYouAwake)). The one documented exception is clamshell mode, which needs AC power, an external display and external input ([Apple Community](https://discussions.apple.com/thread/251885921)). That source is a community answer, and Apple's own clamshell support pages could not be fetched. A dummy HDMI or USB-C plug is reported to satisfy the display requirement ([braindetox](https://braindetox.kr/en/posts/electronic_clam_clamshell_agent_2026.html)), and the M3 14" has an HDMI port, so a plug should fit directly, though the port set was not verified. Dummy plugs list at roughly Rs 120-399 in India ([IndiaMART](https://m.indiamart.com/impcat/hdmi-plug.html)). Detection is not guaranteed. An M1 Air on macOS 26.2 still slept with a hub plus dummy display ([MacRumors](https://forums.macrumors.com/threads/input-is-not-working-with-closed-lid.2475561/)). A homelab user also saw a Mac sleep about an hour into clamshell despite `pmset sleep 0`, and added Amphetamine as a second layer ([travis.media](https://travis.media/blog/mac-homelab-ai-agent-server)). A user on an M3 Pro found that clamshell with an external monitor sleeps when the charger is unplugged, and community replies say clamshell has never worked without power ([Apple Community](https://discussions.apple.com/thread/255659435)). Treat clamshell as AC-only.

`pmset -a disablesleep 1` is the only switch reported to override lid-close sleep without a display. Apple does not document it, and it is absent from the pmset man page mirror ([pmset(1)](https://keith.github.io/xcode-man-pages/pmset.1.html)). Evidence that it works comes from a vendor claim of success on Apple Silicon under macOS 26.3 ([Sleepless](https://aboudjem.github.io/Sleepless/)) and from a MacRumors user who confirmed it works on battery ([MacRumors](https://forums.macrumors.com/threads/prevent-macbook-air-m2-sleep-when-lid-is-closed.2358380)). That is thin evidence, so VOID must read the flag back (`pmset -g | grep SleepDisabled`) rather than assume success. The flag is a blunt instrument. If forgotten, the Mac never sleeps even on battery, and the internal display can stay lit at full brightness under the lid ([braindetox](https://braindetox.kr/en/posts/electronic_clam_clamshell_agent_2026.html); [Gadget Hacks](https://apple.gadgethacks.com/how-to/how-to-keep-macbook-awake-with-lid-closed-3-scenarios-explained/)). The OS's own forced sleeps, such as a critically low battery or a thermal emergency, still override it ([Gadget Hacks](https://apple.gadgethacks.com/how-to/how-to-keep-macbook-awake-with-lid-closed-3-scenarios-explained/); [Apple QA1340](https://developer.apple.com/library/archive/qa/qa1340/_index.html)). Amphetamine 5.0 and later offer a "keep awake with display closed" setting ([Amphetamine support](https://iffy.freshdesk.com/support/solutions/articles/48000078314--amphetamine-does-not-keep-my-mac-awake)). Its mechanism is undisclosed, results on M2 Airs were mixed, and a second-hand report says it fails on Apple Silicon when the power source changes ([Sleepless](https://aboudjem.github.io/Sleepless/)). It is a fallback, not a foundation. Sleepless shows the safer packaging for `disablesleep`. It uses a sudoers rule limited to exactly `pmset -a disablesleep 0|1`, an auto-off at a battery floor (default 15%), an off-switch in Low Power Mode, and a timer ([Sleepless](https://aboudjem.github.io/Sleepless/)). Whether macOS 26.4+ changed any of this is unknown.

## Freezing other apps saves CPU but not memory, and failure is the real risk

Frost, a small open-source freezer (two commits, zero stars, so low maturity), sends SIGSTOP to an app and its child processes, persists frozen PIDs, validates PID plus process name, and resumes leftovers on its next launch ([Frost](https://github.com/Yessi-cmd/Frost)). It excludes VPN and proxy apps so connectivity survives. App Tamer, the mature commercial reference, can stop an app, demote it to efficiency cores, or cap its CPU share, and it is current through macOS 26 ([App Tamer](https://www.stclairsoft.com/AppTamer/)). Two lessons carry over. First, a stopped Chromium or Electron app has helper processes, so the whole descendant tree must be handled. Second, stop/continue works for ordinary same-user apps, since both tools ship on it. No source documents what actually breaks. Likely failure modes are timed-out sockets, beachballing Dock entries, cut-off audio, and confused helper services on resume, and all of these are unverified general knowledge that needs testing. One mechanical point is safe to rely on. A stopped process queues SIGTERM until it is continued, so VOID must SIGCONT before any quit attempt (general knowledge, unsourced).

The gentler alternative is `taskpolicy -b -p PID`. Background QoS is the only class confined to efficiency cores, and those threads cannot be promoted to P cores even when the P cores are idle ([Eclectic Light](https://eclecticlight.co/2025/05/09/what-is-quality-of-service-and-how-does-it-matter/)). Oakley calls it "a brake, but not an accelerator" and reports that `renice` made no detectable difference on Apple Silicon ([Eclectic Light](https://eclecticlight.co/2022/10/20/making-the-most-of-apple-silicon-power-5-user-control/)). App Nap is automatic and mild. Apple says its measures mainly reduce the impact on other apps and "don't necessarily save energy" ([Apple App Nap doc](https://developer.apple.com/library/content/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/AppNap.html)). Housekeeping such as Spotlight, update checks and XProtect already runs on efficiency cores ([Eclectic Light](https://eclecticlight.co/2025/07/18/save-your-m-series-macs-energy-and-battery/)). Root-owned daemons such as mds and photoanalysisd are out of reach without root (inferred, unverified), and no idle-load numbers were found for them. With the display off, WindowServer compositing for other apps should shrink, since its cost scales with windows ([Eclectic Light](https://eclecticlight.co/2022/02/19/explainer-windowserver/)). So the residual cost is mostly background CPU from stray apps and bursty daemons.

On 8 GB the binding constraint is memory. No throttle, stop or hide frees RAM. A stopped process keeps its footprint, though macOS may compress or swap it under pressure (unverified). Only quitting frees memory, at the cost of state, and a polite terminate can raise save dialogs nobody will see under a closed lid. So SIGSTOP is worth shipping only as an opt-in, targeted tool. It suits a short, user-chosen list of apps that actually wake constantly, such as chat apps and Electron clients. A "freeze everything else" default is the wrong shape. The verdict is that it is safe enough when it is default-deny, allowlist-protected, time-boxed and watchdog-backed, and not worth it otherwise. A threshold on memory pressure and an actual CPU measurement should decide whether to act at all.

## Voice and audio need an external path, and the phone is the best one

Apple's security documentation says Apple Silicon and T2 laptops disconnect the microphone in hardware when the lid closes, and that this holds even against root and kernel software ([Apple Platform Security](https://support.apple.com/guide/security/secbbd20b00b/web)). The page does not name the 14" MBP specifically, but an Apple Community specialist applies it to Apple Silicon generally ([Apple Community](https://discussions.apple.com/thread/254343918)). AppleCare has told a user the same, even with an external monitor attached ([Apple Community](https://discussions.apple.com/thread/8566471)). The built-in camera is simply covered by the lid. VOID therefore needs one of these paths. The first is the Android mic over the existing WebSocket, with wake word or push-to-talk handled on the phone. That needs no new hardware. The second is a USB or Bluetooth mic or headset. The third is a dedicated wake-word satellite such as an ESP32 or ATOM Echo, which Home Assistant documents at about $13 but which is overkill for one user ([Home Assistant](https://home-assistant.io/voice_control/about_wake_word)). iPhone Continuity mic is reported flaky, and the user's phone is Android anyway ([MacRumors](https://forums.macrumors.com/threads/use-your-iphone-as-a-microphone-for-your-mac.2457447/page-2)). One more risk is that the default input device may change when the lid closes ([CloudTalk](https://help.cloudtalk.io/en/articles/7007452-known-issue-microphone-not-working-with-macbook-lid-closed)). VOID should bind its capture to a specific device UID rather than the system default, and fail loudly if that device disappears.

Output is less well documented. No fetched source confirms whether the built-in speakers play under a closed lid without an external display. Bluetooth is the weak point. Closed-lid Macs have been reported to keep grabbing speakers and AirPods ([Apple Community](https://discussions.apple.com/thread/253636053)). A Bluetooth speaker dropped about a minute after each reconnect in a lid-closed dock setup ([MacRumors](https://forums.macrumors.com/threads/bluetooth-speaker-disconnects-when-lid-macbook-is-closed.2227333)). An M4 Pro owner tied closed-lid heat to the Mac searching for absent Bluetooth devices ([Apple Community](https://discussions.apple.com/thread/256249778)). Chrome playing YouTube Music is itself an audio client, so it also needs a stable output route. For this reason, the best arrangement is to send VOID's spoken replies to the phone through the same link, and to use a wired or USB speaker for music. Both are inferences to verify on the device.

## Heat, battery and FileVault set the safety envelope

Closing the lid blocks the heat path through the keyboard deck. Vendors advise caution with sustained heavy load, and call light unattended work fine ([Sleepless](https://aboudjem.github.io/Sleepless/); [braindetox](https://braindetox.kr/en/posts/electronic_clam_clamshell_agent_2026.html)). Community evidence on clamshell overheating is anecdotal and mostly from older Airs, with some users noting more frequent fan use and a hot chassis ([MacRumors](https://forums.macrumors.com/threads/mba-overheating-in-clamshell-mode-myth.2012525/)). No measured M3 14" closed-lid data exists. A local LLM plus TTS on 8 GB is the worst case, because memory pressure and swap add heat on top of reduced airflow. Apple states that notebooks work best at 10-35 C ambient and that heat above 35 C can permanently reduce battery capacity ([Apple Batteries](https://www.apple.com/batteries/maximizing-performance/)). Charge Limit (80-100%) exists on Apple Silicon Macs from macOS Tahoe 26.4, under Battery settings ([Apple Support](https://support.apple.com/102338)). Set it to 80% for a Mac that lives on the charger. Keep the Mac on a stand with open air around it. Never put a sleep-disabled Mac in a bag, which is the one scenario where the flag turns a convenience into a fire-adjacent hazard. Ordinary advice is to revert the flag or shut down first.

FileVault does not conflict with closed-lid operation while the Mac stays up, because processes keep running behind the lock screen. This matches how VOID's lock-screen UI already works, but no source confirmed it on macOS 26. A reboot is the problem, since FileVault stops at a pre-boot password with no network or SSH until someone types it locally. A planned restart can use `fdesetup authrestart` ([Astropad](https://astropad.com/blog/filevault-headless-mac-mini/)). Keeping FileVault on and accepting a manual unlock after power loss is the better security trade than disabling it for auto-login. One more wrinkle is that a display hot-plug change on a dock or KVM can force a re-login on Apple Silicon, per a vendor account ([TESmart](https://www.tesmart.com/blogs/case/from-edid-confusion-to-system-insight-how-a-customer-drove-our-understanding-of-macos-clamshell-behavior)). That is a reason to avoid reconnecting the dummy plug while VOID is running.

## Ranked recommendation and concrete improvements to VOID's design

The ranking below rests on the evidence above, and it favours the lowest-risk path that still works.

| Rank | Setup | Why |
|---|---|---|
| 1 | AC power plus dummy HDMI plug (about Rs 150-400) for clamshell, VOID's `disablesleep` toggle as a backup, phone as mic, Charge Limit 80%, Mac on a stand | Clamshell is the supported path and less fragile than software hacks, per the braindetox guide. Power is mandatory. |
| 2 | Same as rank 1, plus a USB or Bluetooth mic near the desk | Gives a wake path independent of the phone. Mic prices are unsourced. |
| 3 | `disablesleep` alone with lid closed, on AC | Works without hardware but has no OS guardrails and risks a lit display and heat. |
| 4 | `disablesleep` on battery | Allowed by the flag but drains the battery and heats the machine. Avoid except for short sessions. |
| 5 | Third-party keep-awake apps alone | Assertion-based apps cannot beat lid-close sleep. Amphetamine 5.x is unverified here. |

For the existing design, the toggle that runs `pmset disablesleep` through an admin prompt should change first. Replace the repeated admin prompt with a narrowly scoped sudoers rule, or a privileged helper installed through SMAppService, covering only `pmset -a disablesleep 0|1`. That is the packaging Sleepless uses ([Sleepless](https://aboudjem.github.io/Sleepless/)). Whatever the packaging, always read the real state back with `pmset -g | grep SleepDisabled`, and show that state, not the toggle's last position, in the menu bar. Add guardrails that raw `disablesleep` lacks. These are a battery floor (default 15%), automatic off in Low Power Mode, a maximum duration timer, a warning when the Mac is on battery, and a thermal check using `ProcessInfo.thermalState` that backs off or warns on "serious". Zero the internal display brightness or sleep the display on lid close, since the raw flag can leave it lit. Run an input-device pin, and an audible or phone-side alert if the pinned mic disappears. Clear the flag on quit, and on next launch detect a flag VOID set earlier and offer to clear it, so a crash cannot leave the Mac permanently awake. Make clamshell detection a first-class mode, so the app prefers AC plus a display and uses `disablesleep` only when no display is present.

For the "pause other apps" feature, keep the allowlist, lid-open resume, quit resume and PID persistence, and harden them with the following changes. Persist start time along with PID and name, because PIDs get reused. Make the default a user-chosen pause list rather than "everything else", and always protect VOID and its children, Chrome with all helpers, anything holding audio output, network and VPN tools, Finder, Dock, loginwindow, SystemUIServer and ControlCenter. Stop the whole descendant tree, helpers first, and continue the parent first. The persisted file is not enough alone, because Frost-style recovery only happens if the controller is relaunched. Add a tiny independent watchdog, such as a LaunchAgent that SIGCONTs the persisted PIDs if VOID's PID disappears, plus SIGTERM, SIGINT and SIGHUP handlers, a maximum-freeze timer, and a one-click "Resume all". Add graduated escalation, applying `taskpolicy -b` first and SIGSTOP only to apps measured as heavy. Gate the whole feature on memory pressure and measured CPU so it does nothing when it would not help. Detect lid state through IOKit (`AppleClamshellState` on `IOPMrootDomain`, a property name taken from general knowledge and not verified) or by polling, and log every stop and continue for debugging.

## Conclusion

The research reframes the question. "Only VOID runs" is not a power-management problem, because macOS sleeps as one unit, so the achievable target is a cool, quiet, whole-machine awake state with VOID as the only meaningful workload. Seen that way, the dummy plug on AC power is the cheapest way to make the closed lid a supported configuration, `disablesleep` is a fallback that needs guardrails, and per-app freezing is a marginal optimisation on an 8 GB machine that cannot free any RAM.

Several load-bearing facts remain unverified and justify a one-evening test before relying on this. The checks are whether the dummy plug triggers clamshell on this M3 14", whether `disablesleep` still behaves on the current macOS 26.x, whether the built-in speakers play under a closed lid, how the Android mic path behaves at the lock screen, and what temperatures a 30-minute MLX load reaches with the lid closed. A heartbeat process plus `pmset -g log` and `pmset -g assertions` would answer the first two directly.
